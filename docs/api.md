# API

A REST API built with Django REST Framework. The schema is generated by drf-spectacular. The
frontend uses a TypeScript client generated from that schema, so the two can't drift silently.

- **Interactive docs (Swagger UI):** `/api/docs/`, for example http://localhost:8000/api/docs/
  with the default ports.
- **OpenAPI schema (YAML):** `/api/schema/`.
- **Typed client:** `make types` writes the schema to
  [frontend/src/lib/api/schema.yml](../frontend/src/lib/api/schema.yml) and generates
  [schema.d.ts](../frontend/src/lib/api/schema.d.ts) with `openapi-typescript`. Server Components
  and Client Components both call the API through `openapi-fetch` with those types.

This page covers the conventions the schema can't express, the endpoint list, and the error
codes. Field-level request and response shapes are in Swagger.

## Conventions

**Same origin.** The browser calls `/api/*` on the frontend's origin, and Next proxies it to
Django. Cookies are first-party, and there is no CORS configuration. Django URLs end in `/`.
See [architecture.md](architecture.md#request-paths).

**Authentication.**
- Every endpoint requires a Django session unless it opts out. The opt-outs are the catalog,
  health, stats, the auth endpoints and the webhook.
- An unauthenticated request gets **401**. The custom `SessionAuthentication` sends a
  `WWW-Authenticate` value, which is what makes DRF answer 401 instead of 403.
- A CSRF or permission failure gets **403**.
- Unsafe requests need `X-CSRFToken`, read from the `csrftoken` cookie.
- **Django rotates the CSRF token at every login.** This is
  [Django's built-in behaviour](https://docs.djangoproject.com/en/6.1/ref/csrf/#why-might-a-user-encounter-a-csrf-validation-failure-after-logging-in): `django.contrib.auth.login()` calls `django.middleware.csrf.rotate_token()`.
  It isn't project code. It's the reason the browser client reads the cookie on every request
  instead of caching the token.

Details are in [flows/auth-and-sessions.md](flows/auth-and-sessions.md).

**404 instead of revealing existence.**
- Another user's order or cart line is a **404**, not a 403.
- Every `/api/staff/*` endpoint answers **404** to anonymous and non-staff users (`IsStaffOr404`).

A 403 would confirm that the thing exists.

**Query parameters are validated by a serializer.**
- A bad value is a **400** with a message per field, for example
  `{"max_price": ["Must be greater than or equal to min_price."]}`.
- The same serializer documents the parameters in the OpenAPI schema via
  `extend_schema(parameters=[…])`.

**Strict pagination** (`StrictPageNumberPagination`):
- A malformed `page` or `page_size` (`abc`, `0`, above the maximum) is a **400**. DRF's default
  would silently ignore it or return 404.
- A valid page past the end is a **404**.
- Responses are DRF's `{count, next, previous, results}`.

**Money is a decimal string**: `"75.01"`, never a JSON number. Floats can't represent cents
exactly, and the client formats strings with `Intl.NumberFormat`. Aggregates in analytics follow
the same rule.

**Every output field is always present.** Output serializers set
`read_only_fields = fields`, so the generated TypeScript types mark every field as required. The
client never has to handle a field that might be missing.

**Order URLs use the 32-hex `external_id`**, never the database id.

**Query counts are pinned by tests.** An N+1 regression fails the test suite (there is no CI
workflow yet). The pinned endpoints:
- the four catalog endpoints, with exact counts (`django_assert_num_queries`);
- `GET /api/cart/`, `GET /api/orders/` and `GET /api/orders/{id}/`, with upper bounds
  (`django_assert_max_num_queries`).

The staff endpoints have no query-count tests yet ([testing.md](testing.md)).

## Errors

DRF's own errors keep DRF's shape: `{"field": ["message"]}` for validation, `{"detail": "…"}`
otherwise.

Business-rule failures are **domain errors**. These are plain Python exceptions raised by
services ([backend/apps/core/errors.py](../backend/apps/core/errors.py)). One exception handler
turns them into `{code, detail, …}` with the error's status
([backend/apps/core/exceptions.py](../backend/apps/core/exceptions.py)). Services don't import
anything from DRF, so Celery tasks, management commands and tests call them directly.

| `code` | HTTP | When | Extra fields |
|---|---|---|---|
| `empty_cart` | 400 | Checkout with an empty cart | — |
| `out_of_stock` | 409 | Checkout when a line asks for more than the stock | `lines: [{offer_id, product, requested, available}]` |
| `invalid_transition` | 409 | Cancel or pay on an order that isn't unpaid; any illegal state move | `current_status` |
| `reservation_expired` | 409 | Starting a payment after the stock hold expired | `current_status` |
| `idempotency_conflict` | 409 | The same `Idempotency-Key` with a different request body | — |
| `replay_read_only` | 409 | Cancel, payment or return on a replayed historical order | — |

The frontend picks its message by `code` (checkout form, order actions) and falls back to `detail`.

## Idempotency-Key (checkout)

`POST /api/checkout/` is the one endpoint where a retry must not repeat the action (a second
order, stock taken twice). It requires an `Idempotency-Key` header: 8–255 URL-safe characters,
generated in the browser per checkout attempt and reused on retry
([frontend/src/lib/checkout-attempt.ts](../frontend/src/lib/checkout-attempt.ts)).

The behaviour comes from `run_idempotent` in
[backend/apps/core/idempotency.py](../backend/apps/core/idempotency.py):

- **Keys are per user.** The key row is inserted **in the same transaction** as the checkout,
  with a hash of the request body. When the checkout succeeds, its response is stored on that
  row.
- **The same key with the same body** returns the stored response, with the header
  `Idempotent-Replayed: true`.
- **The same key with a different body** is a `409 idempotency_conflict`.
- **Failures aren't stored.** A domain error rolls back the key row too, so a retry after
  "out of stock" runs again.
- **Concurrent duplicates.** The second request blocks on the unique index until the first
  commits, then replays its response.
- **Expiry.** Keys expire after 24 h (`IDEMPOTENCY_KEY_TTL_HOURS`). A daily task (03:15 UTC) purges them.

Starting a payment needs no key: a partial unique index allows one open `PaymentIntent` per
order, so a repeated click reuses it ([data-model.md](data-model.md#constraints-that-carry-business-rules)).
